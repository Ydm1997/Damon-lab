# 一、面试总定位

## 1. 一句话职业定位

我是偏**技术型解决方案工程师 / 海外售前技术支持工程师**的人选，具备机器人、SLAM、RTK/GNSS、多传感器融合、嵌入式系统和智能硬件产品经验，能够把复杂技术能力转化为客户听得懂、销售能推进、研发能处理、项目能落地的解决方案。

## 2. 简历主线

面试时不要把经历讲散，要始终围绕这一条主线：

> **机器人 / 空间感知技术基础 → 客户场景需求拆解 → 行业方案与演示材料输出 → 产品验证与技术答疑 → 客户问题追踪与研发闭环。**

这条主线可以支撑以下岗位：

- 机器人解决方案工程师
    
- 海外售前方案工程师
    
- 技术支持工程师
    
- 空间感知 / 三维重建产品解决方案
    
- 智能硬件行业解决方案
    
- 机器人教育解决方案
    
- 数据产品 / 空间数据服务相关岗位
    

## 3. 面试中的安全边界

可以重点说：

- 我参与过手持 SLAM 扫描设备的研发验证、产品测试、客户技术支持和行业方案输出；
    
- 我理解 SLAM、RTK/GNSS、IMU、激光雷达、摄像头、多传感器融合和点云采集在产品中的作用；
    
- 我做过客户需求拆解、方案材料、演示 SOP、FAQ、测试报告、竞品分析、Issue 整理和研发反馈；
    
- 我参与过日本、北欧等海外客户支持和英文材料整理，但不是所有海外项目都由我独立主导；
    
- 我参与过集群机器人科研成果向教学产品、演示 Demo 和教育项目方案的转化。
    

不要过度说：

- 不要说自己是 SLAM 核心算法负责人；
    
- 不要说日本、北欧项目全流程由自己独立负责；
    
- 不要说自己能独立完成大模型 / 具身智能算法训练；
    
- 不要说自己是传统销售或负责最终商务成交；
    
- 不要把教育机器人项目包装成大型工业机器人商业落地项目。
    

## 4. 最稳的人设表达

> 我的优势不是单点算法深度，而是能理解技术链路、拆解客户场景、输出方案材料、支持演示验证，并把客户问题结构化反馈给研发团队推动闭环。

# 三、岗位匹配逻辑：云深处 / 机器人海外售前

## 1. 云深处海外售前方案工程师的核心任务

这个岗位不是简单销售支持，而是海外客户、销售、代理商、研发和交付团队之间的技术桥梁。核心任务通常包括：

1. 面向海外客户做需求挖掘；
    
2. 针对巡检、救援、建筑、测绘、林地、安防等特种行业场景输出方案；
    
3. 配合销售完成技术交流、方案宣讲、产品演示、代理商培训；

一句话理解：

> 海外售前方案工程师的核心价值，是把机器人能力转化为海外客户可理解、可验证、可落地的行业解决方案。

# 四、四个核心项目案例

[!tip] 案例表达总原则 不要讲成“我一个人主导整个项目”，而要讲成：我参与了客户场景需求拆解、售前技术材料准备、演示流程设计、测试结果整理、客户问题答疑和研发问题闭环。我更核心的价值，是把客户现场问题转化成技术团队能理解、销售团队能推进、客户能够判断的解决方案语言。

回答结构建议：

> 背景是什么 → 客户担心什么 → 我怎么拆解 → 我做了什么 → 结果沉淀了什么 → 对目标岗位有什么迁移价值。

## 案例一：工业级手持 SLAM + RTK 高精度感知终端方案落地

### 1. 30 秒面试短版

我参与过工业级手持 SLAM + RTK 高精度感知终端项目，面向测绘、建筑、巡检、林地等客户。产品涉及激光雷达、IMU、GNSS、摄像头、多传感器融合、SLAM 建图和点云采集。我主要做场景需求拆解、产品验证支持、行业方案材料、演示 SOP、FAQ、竞品分析和海外 Issue 闭环。这个项目锻炼了我把复杂空间感知技术转化成客户场景价值的能力。

### 2. 2 分钟完整讲述版

这个项目面向测绘、建筑、巡检、林地测量等专业客户，产品涉及激光雷达、IMU、GNSS、摄像头、多传感器融合、SLAM 建图、点云采集和三维重建。客户重点关注点云质量、轨迹稳定性、室内外切换表现、弱 GNSS 环境适应能力和数据传输稳定性。

不同客户的关注点不一样。建筑客户关注室内外切换、边缘点云噪声、墙面重影、门窗结构是否清晰；林地和测绘客户关注树林遮挡、弱 GNSS、轨迹漂移和坐标成果；巡检客户关注作业效率、设备稳定性、数据完整性和成果复核；海外客户关注部署效率、英文材料、售后响应、数据上传和现场环境适应性。

我的工作主要有四类。

第一，做场景需求拆解。把客户场景拆成采集环境、作业流程、关键技术指标、风险边界和成果输出。例如建筑场景重点看室内外切换和边缘点云；林地场景重点看弱 GNSS 和遮挡；海外场景重点看部署效率和数据传输。

第二，参与产品验证和测试材料整理。围绕激光雷达、IMU、GNSS、摄像头等多传感器链路，协助记录点云质量、建图稳定性、数据传输、设备部署等问题，整理测试报告和点云效果对比图。

第三，输出行业方案和演示材料。整理行业解决方案、产品演示 SOP、英文 PPT、FAQ、竞品分析和技术建议书，把 SLAM、多传感器融合、时间同步、点云厚度、重建速度等技术概念转成客户能理解的表达。

第四，推动问题闭环。把客户现场反馈整理成 Issue，包括问题类型、场景、版本、复现步骤、影响程度和建议排查方向，同步销售、研发、算法、硬件和交付团队处理。

这个项目最后沉淀了产品演示 SOP、竞品对标材料、英文技术说明、客户测试报告、技术建议书和 Issue 追踪机制，支撑销售团队完成复杂技术场景下的客户沟通，也推动产品在海外复杂场景中的验证和优化。

### 3. 面试追问

#### Q1：你在这个项目中最核心的价值是什么？

**回答：**

## 案例二：日本建筑工地客户手持 SLAM 技术支持

### 1. 30 秒面试短版

### 2. 2 分钟完整讲述版

我参与的重点不是独立负责整个海外项目，而是参与售前技术支持和材料准备。我首先把客户的问题进行分类：第一类是点云质量问题，比如点云厚度、重影、边缘噪声；第二类是轨迹和建图稳定性问题，比如室内外切换、弱 GNSS 环境、重复路径；第三类是操作流程问题，比如采集速度、路线规划、设备初始化和数据导出；第四类是成果可用性问题，比如点云能不能用于测量、建模或后处理。

在材料准备上，我参与整理了英文 PPT、测试报告、点云效果截图和 FAQ。比如客户问“为什么边缘会有噪声”，我不会简单回答“算法会优化”，而是会结合建筑场景的反射材质、设备运动速度、激光扫描角度、轨迹估计误差和多传感器同步来解释。客户问“室内外切换是否会偏移”，我会说明 GNSS、IMU、LiDAR SLAM 在不同环境下各自发挥的作用，以及现场验证时应该如何设计采集路线。

这个案例最后沉淀了英文技术说明、演示 SOP、测试报告、FAQ 和客户问题记录。对我来说最大的收获是，海外售前方案工程师不能只讲参数，而要围绕客户真实工况建立一套“可验证、可解释、可复现”的技术沟通方式。

如果迁移到四足机器人或轮足机器人海外售前岗位，逻辑是相通的。机器人进入日本建筑、巡检、隧道、工厂等场景时，客户同样会关注稳定性、安全性、地形通过能力、任务复现能力和售后响应。我的优势是能把这些客户问题拆成技术指标、测试方案、演示流程和风险边界，帮助客户完成技术判断。

## 案例三：北欧复杂环境客户问题闭环

### 1. 30 秒面试短版

我参与过北欧复杂环境下的手持 SLAM 设备客户支持。北欧场景比较特殊，可能涉及高纬度卫星信号弱、低温环境、现场网络不稳定、数据上传异常等问题。我的工作重点是把客户反馈从一句“设备不稳定”拆解成采集链路、定位链路、通信链路、软件版本、现场操作和数据保存几个环节，再整理 Issue 表同步研发团队。这个案例锻炼了我把海外客户模糊反馈转化成研发可复现、可判断、可闭环问题的能力。

### 2. 2 分钟完整讲述版

我还参与过一个北欧复杂环境下的海外客户支持案例。这个项目和日本建筑场景不太一样，日本客户更偏建筑空间采集和点云质量验证，而北欧场景更突出环境复杂性和系统稳定性。

客户反馈的问题包括高纬度地区卫星信号弱、低温环境下设备稳定性需要验证、现场数据上传不稳定、WiFi 5G 链路偶发异常、虚拟串口通信异常、点云显示或保存不流畅等。这类问题的难点在于，它们往往不是单一模块导致的。如果客户只说“数据传不上去”或者“设备不稳定”，研发团队很难直接定位。

我当时参与的主要工作，是把客户反馈结构化。我会先确认问题属于哪一类：是采集端没有正常生成数据，还是通信链路传输不稳定；是 WiFi 网络环境问题，还是软件接收端处理不及时；是虚拟串口通信异常，还是最终保存或显示阶段出了问题。

比如面对“数据上传不稳定”这个问题，我会把它拆成几个环节：第一，设备端点云或图像数据是否正常生成；第二，数据打包和发送频率是否正常；第三，WiFi 5G 链路是否稳定；第四，虚拟串口通信是否存在丢包或阻塞；第五，接收端软件是否正常解析；第六，最终保存结果是否完整。这样问题就从一个模糊描述，变成了可以逐项排查的技术链路。

在问题记录上，我会整理客户现场环境、设备版本、软件版本、操作步骤、复现频率、截图、日志、影响程度和初步判断，形成 Issue 表同步研发团队。对于海外客户来说，时差和现场沟通成本都比较高，如果一次反馈信息不完整，就会来回消耗很多时间。所以我理解海外售前和技术支持的一个重要能力，就是减少信息损耗。

这个案例最终沉淀的是一套海外问题闭环的方法：客户反馈不是简单转发，而是要做分类、补充上下文、判断优先级、同步研发、跟进版本验证，再反馈给客户。

如果放到机器人产品上，类似场景会更多。比如机器人在海外巡检、应急、矿区、隧道、林地等场景运行时，客户可能反馈“机器人走不稳”“任务中断”“网络断开”“导航失败”“低温续航下降”。解决方案工程师不能只把问题丢给研发，而是要把它拆成运动控制、感知定位、通信链路、电池温度、地形条件、任务脚本、后台平台等模块，推动问题闭环。

### 3. 面试追问

#### Q1：北欧项目里你具体解决了什么问题？

**回答：**

我更准确的表达是：我参与了问题拆解、链路分析、Issue 整理和研发反馈，不会说所有底层问题都是我独立解决的。比如数据上传不稳定，我会从采集端、通信链路、虚拟串口、接收端、保存端去拆解，并收集版本、日志、复现步骤和影响程度，帮助研发团队更快判断问题方向。

#### Q2：海外客户问题闭环最重要的是什么？

**回答：**

我认为最重要的是信息结构化和响应确定性。海外客户现场成本高、沟通链路长，如果问题描述不清楚，研发很难定位，客户也会觉得我们不专业。所以我会尽量把问题写成标准 Issue，包括场景、版本、操作步骤、现象、期望结果、复现概率、影响程度、附件证据和下一步动作。这样客户、销售、研发都知道问题处在什么阶段。

#### Q3：如果客户在低温环境下反馈设备不稳定，你会怎么问？

**回答：**

我会先确认低温具体范围、设备工作时长、电池状态、是否出现自动关机或性能下降、传感器是否正常、网络是否稳定、问题发生在启动阶段还是运行阶段。然后判断是电池低温性能、传感器工作范围、结构防护、软件异常还是通信链路问题。对客户我不会立刻承诺结论，而是会说明需要按环境、硬件、电源、传感器、软件日志几个方向排查。

#### Q4：你说优化 WiFi 5G 传输和虚拟串口通信，是你改代码了吗？

**回答：**

这个要分情况。我不是把所有底层代码都独立完成的人，我更多参与的是现场问题整理、通信链路分析、复现信息收集和研发反馈。如果涉及具体底层修改，会由研发团队确认和实现。我能做的是把问题拆清楚，提供复现条件和影响判断，减少研发排查成本。

## 案例四：温州集群机器人教育场景转化

### 1. 30 秒面试短版

我在中国科学院大学温州研究院期间，参与过集群机器人从科研项目向教育场景转化的工作。这个项目不是单纯做机器人研发，而是把路径规划、PID 控制、避障巡逻、集群协同等技术能力，转化成学校客户能看懂、能采购、能落地的教学 Demo 和项目方案。我参与机器人排队、避障巡逻、路径跟随等演示设计，也整理人工智能实训室、机器人社团、科创课程、招投标技术参数和交付材料。这个经历让我具备把机器人技术翻译成客户业务语言的能力。

### 2. 2 分钟完整讲述版

在中国科学院大学温州研究院期间，我参与过一个集群机器人教育场景转化项目。这个项目的背景是，研究院有一些机器人科研成果，底层涉及机器人控制、路径规划、PID 控制、避障巡逻、队列控制、集群协同等能力。但客户主要是中小学、职业院校、人工智能实训室和科创教育场景，他们并不会直接关心底层算法有多复杂，而是关心机器人能不能用于课程、学生能不能参与、老师能不能上手、学校能不能展示成果、项目能不能验收和持续使用。

所以我参与这个项目时，重点不是把技术讲得更深，而是把技术讲得更容易被客户理解。比如路径规划，如果对学校客户讲算法，他们可能感受不强；我会把它转化成“机器人可以从 A 点到 B 点自主完成任务”。PID 控制可以转化成“机器人偏离路线后能够自动修正”。避障算法可以转化成“机器人遇到障碍物后能够绕行”。集群协同可以转化成“多台机器人按照队形或任务规则一起执行动作”。

在 Demo 设计上，我参与了机器人排队、避障巡逻、路径跟随等可视化演示。这样的 Demo 更适合学校客户，因为老师和学生可以直观看到机器人如何感知、决策和行动，也更容易和课程、社团、科创活动结合起来。

在方案材料上，我参与整理过人工智能实训室、机器人社团、科创课程和项目式学习相关材料，包括设备配置建议、课程展示脚本、项目建设方案、技术参数表、项目汇报材料和招投标技术内容。招投标材料里，我会把产品技术参数、功能清单、交付内容、售后服务、硬件维保范围和项目验收方式写清楚，避免后期交付边界不清。

在现场反馈方面，我也发现教育客户很关注上手难度和稳定性，比如 WiFi 组网流程是否复杂、教师能不能独立使用、学生能不能快速参与。这个过程让我理解：教育机器人解决方案不是简单卖设备，而是要把产品、课程、活动、空间、展示、验收和维护整合起来。

这个经历迁移到机器人海外售前岗位，也有价值。因为本质上都是把复杂机器人技术转化成客户能理解、能测试、能采购、能交付的方案，只是客户从学校变成了建筑、巡检、林地、应急救援等特种行业。

### 3. 面试追问

#### Q1：你在温州机器人项目里写了多少代码？

**回答：**

我不是这个系统的核心算法负责人，更多参与的是应用 Demo 设计、演示逻辑整理、方案材料、客户沟通和交付反馈。但我有电子信息、嵌入式、C/C++、通信和系统调试基础，能够理解路径控制、PID 控制、通信、传感器和系统联调的基本逻辑，也能和研发沟通演示需求和客户反馈。我的主要价值是把机器人技术能力转化成教育客户能看懂、能采购、能落地的方案。

#### Q3：你怎么把机器人技术讲给非技术客户？

# 五、简历深度追问与标准回答

## Q1：你为什么求职解决方案工程师 / 技术支持工程师？

**回答：**

因为我的经历本身就在研发、产品、客户和销售之间。单纯研发更偏实现，传统销售更偏商务，而我过去做得更多的是把技术产品放到真实客户场景里验证，然后输出方案、演示、测试报告和问题闭环。

比如手持 SLAM 设备，研发关心算法、同步、点云和数据链路，但客户关心的是现场能不能采、点云能不能用、弱 GNSS 环境会不会出问题、数据上传是否稳定。我比较擅长把这些技术能力转成客户语言，也能把客户模糊反馈转成研发可定位的问题单。

所以我求职解决方案岗位，不是离开技术，而是希望把技术能力放到更靠近客户和落地的位置。

## Q2：你简历里写“原嵌入式开发”，为什么现在转解决方案？

**回答：**

我不是完全从零转方向，而是从工程开发和产品验证逐步靠近客户场景。在嵌入式或设备类产品里，很多问题不是写完代码就结束，而是要看真实环境下能不能稳定运行。比如手持 SLAM 设备涉及传感器采集、数据同步、通信链路、点云显示和数据导出，一旦到客户现场，问题会从单点技术变成系统问题。

我发现自己比较适合做这种连接型工作：既能理解底层链路，也能和客户沟通现场问题，还能整理 SOP、FAQ、测试报告和 Issue 反馈研发。所以转向解决方案，其实是把原来的技术基础延伸到客户场景和项目落地中。

## Q3：你对 SLAM、RTK、多传感器融合到底掌握到什么程度？

**回答：**

我会真实地说，我不是 SLAM 算法专家，不会把自己包装成核心算法负责人。我对这些技术的掌握主要是工程应用和解决方案层面。

SLAM 方面，我理解它在手持扫描设备中主要解决定位和建图问题，最终体现为轨迹稳定性、点云拼接质量、重影、漂移和建图完整性。

RTK/GNSS 方面，我理解它主要提供全局定位参考，能够提升地理坐标精度，但在室内、树林、高楼遮挡、地下空间和高纬度弱信号环境下会受影响，所以不能只依赖 GNSS。

多传感器融合方面，我理解激光雷达提供空间结构，IMU 提供短时姿态和运动变化，GNSS 提供全局坐标，摄像头提供图像辅助。融合的目标是提升复杂环境下的鲁棒性。

我真正擅长的是把这些技术和客户感知结果对应起来，比如轨迹稳不稳、点云有没有重影、边缘清不清楚、室内外切换会不会偏、成果能不能用于测量和建模。

## Q4：你参与手持 SLAM 设备研发验证，具体做什么？

**回答：**

我参与的研发验证更偏产品化验证和问题定位，不是单纯算法研发。具体有四类工作。

第一是数据链路验证。手持 SLAM 设备涉及激光雷达、IMU、GNSS、摄像头等模块，如果采集异常、同步不稳定、传输卡顿或数据保存异常，最终都会影响点云质量和建图效果。

第二是场景验证。比如建筑场景看室内外切换、墙角边缘、门窗结构和重影；林地测量看树林遮挡、弱 GNSS 和轨迹漂移；巡检场景看效率、稳定性和数据完整性。

第三是问题记录和复盘。把客户现场现象整理成版本、环境、操作步骤、复现概率、日志截图、影响程度和初步判断。

第四是方案和材料沉淀。包括测试报告、点云效果图、演示 SOP、FAQ、英文说明和竞品对标材料。

一句话概括：我的研发验证不是闭门做算法，而是把产品放到真实客户场景里验证，并把问题反馈到研发和产品迭代中。

## Q6：你如何把技术指标转化成客户价值？

**回答：**

我一般从客户业务结果反推技术表达。

比如“弱 GNSS 环境”，研发关注卫星数量、RTK 状态和多路径影响，但客户关心的是室内、树林、高楼遮挡下设备还能不能完成作业。

所以我的表达方式是：技术指标不是单独讲参数，而是讲它对采集稳定性、成果质量、作业效率和交付风险的影响。

## Q10：你如何理解 PoC？

**回答：**

PoC 不是简单试用，而是有明确目标、验证指标和验收标准的小范围可行性验证。

比如手持 SLAM 设备 PoC 前要明确：验证什么场景，是建筑、林地、测绘还是巡检；验证什么指标，是点云质量、轨迹稳定性、弱 GNSS、数据上传还是成果输出；客户验收标准是什么；测试环境是否接近真实场景；双方需要准备哪些设备、场地和人员；风险边界是什么。

## Q11：你如何理解 Issue 闭环？

# 六、机器人与空间感知技术基础问答

## 1. 四足 / 轮足机器人的系统架构

|模块|内容|售前关注点|

|任务载荷|可见光云台、红外热成像、气体检测、喊话器、机械臂|行业任务是否能闭环|
|通信系统|WiFi、4G/5G、专网、遥控链路、数据回传链路|延迟、覆盖、断联策略|

面试回答：

> 我理解四足机器人不是单一机械产品，而是一个集机械、电机驱动、运动控制、SLAM 导航、多传感器融合、通信链路、任务载荷和平台软件于一体的复杂移动机器人系统。海外售前要做的不是只讲机器狗能走多快，而是要根据客户现场，把本体运动能力、感知能力、任务载荷和后台平台组合成完整解决方案。

## 2. ROS2 基础

### ROS2 是什么？

ROS2 是机器人系统中常用的软件框架 / 中间件，常用于机器人模块化开发、节点通信、传感器接入、控制指令分发、状态监控和调试。ROS2 不是传统意义上的操作系统，而是一套机器人软件通信与开发框架。

### ROS2 核心概念

|概念|解释|面试表达|
|---|---|---|
|Node 节点|一个独立功能模块|例如激光雷达节点、相机节点、运动控制节点、导航节点|
|Topic 话题|异步发布 / 订阅通信|适合传感器数据、状态信息、里程计等连续数据|
|Service 服务|请求 - 响应通信|适合查询设备状态、触发一次性动作|
|Action 动作|可取消、可反馈的长任务|适合导航到某点、执行巡检任务等|
|Parameter 参数|运行参数配置|如速度限制、传感器外参、导航参数|
|TF 坐标变换|管理机器人各坐标系关系|base_link、map、odom、lidar、camera 等|
|Launch|启动多个节点|用于一键启动导航、感知、控制系统|
|Lifecycle|节点生命周期管理|用于配置、激活、停用、清理，提高系统可控性|
|QoS|通信质量策略|对传感器数据、弱网络、实时性有影响|

### Q：你是否实际开发过 ROS2？

**回答：**

我目前不是 ROS2 核心开发经验非常深的候选人，之前更多是在嵌入式 Linux、C/C++、Qt、MQTT、传感器数据链路和设备调试上积累经验。但我理解 ROS2 的基本架构，包括节点、话题、服务、Action、TF、参数和生命周期。对售前方案岗位来说，我可以理解客户二次开发、数据接口、传感器接入和系统集成的基本逻辑，也能够和研发团队对齐技术方案。

### Q：ROS2 和 MQTT 有什么关系？

**回答：**

ROS2 更偏机器人内部模块通信和控制框架，MQTT 更常用于设备和云端、App、后台平台之间的消息通信。比如机器人内部传感器、导航、控制可以通过 ROS2 组织，而巡检任务结果、设备状态、告警、视频或点云索引等可以通过 MQTT 或其他协议上报到云平台。我的 MQTT 经验可以迁移到机器人设备端与平台端的数据链路、状态上报和远程控制方案中。

## 3. 运动控制基础

移动机器人运动控制可以按三层理解：

1. **任务层**：客户要机器人做什么，例如巡检、建图、搜索、回充；
    
2. **导航层**：机器人怎么从 A 点到 B 点，包括路径规划、避障、定位；
    
3. **控制层**：机器人如何稳定运动，包括步态控制、姿态控制、电机控制、速度控制。
    

四足机器人的关键控制问题：

|问题|解释|客户价值|
|---|---|---|
|步态控制|控制机器人走、跑、爬楼、跨越障碍|决定复杂地形通过能力|
|姿态控制|保持机身稳定|决定载荷图像稳定和安全性|
|平衡控制|避免跌倒，适应外力扰动|决定可靠性和现场安全|
|路径跟随|按规划路线移动|决定巡检任务是否可重复执行|
|避障控制|动态绕开障碍物|决定无人化巡检能力|
|限速和安全停止|在人员、狭窄空间中降低风险|决定客户是否敢部署|

### Q：PID 怎么讲？

**回答：**

PID 是运动控制中非常基础的闭环控制方法。比如机器人要保持某个速度、角度或路线，系统会不断比较目标值和实际值，再调整控制输出。虽然四足机器人的控制比普通轮式机器人复杂很多，还涉及动力学、步态和姿态控制，但从工程角度看，闭环反馈、误差修正和稳定性仍然是核心思想。

## 4. SLAM 基础

### Q：SLAM 是什么？

**回答：**

SLAM 是同步定位与建图，机器人或扫描设备在未知或半未知环境中，一边估计自身位置，一边构建环境地图。在手持 SLAM 或机器人巡检场景中，它最终体现为轨迹是否稳定、地图是否完整、点云是否重影、任务能否复现。

### Q：特种行业机器人为什么需要 SLAM？

**回答：**

在电力、隧道、管廊、建筑、林地、地下空间等场景中，GNSS 经常不可用或不稳定，机器人需要依靠激光雷达、IMU、相机等传感器完成定位和建图。客户真正关心的不是算法名字，而是机器人能否稳定导航、能否重复执行任务、能否输出可用数据。

### 常见 SLAM 类型

|类型|特点|适用场景|
|---|---|---|
|LiDAR SLAM|精度较高、对光照不敏感|隧道、管廊、室内、夜间巡检|
|Visual SLAM|成本较低、信息丰富|光照条件较好的室内 / 半室外|
|Visual-Inertial SLAM|相机 + IMU，提高短时稳定性|移动机器人、手持设备|
|LiDAR-Inertial SLAM|激光雷达 + IMU，鲁棒性较好|工业巡检、测绘、弱 GNSS 场景|
|GNSS/RTK 融合 SLAM|提供全局坐标约束|室外测绘、林地、园区、道路|

## 5. RTK / GNSS 基础

### Q：RTK 是什么？

**回答：**

RTK 是一种高精度 GNSS 定位技术，通过基准站和移动站之间的差分改正，提高定位精度。它在室外开阔环境中价值很高，可以提供全局坐标参考。但在室内、地下、高楼遮挡、树林和高纬度弱信号环境下，GNSS/RTK 会受到影响，所以在机器人或手持 SLAM 产品中，RTK 通常要和 LiDAR SLAM、IMU 等传感器融合使用。

## 6. 多传感器融合基础

### Q：多传感器融合是什么？

**回答：**

多传感器融合就是把不同传感器的信息结合起来，弥补单一传感器的局限。比如 LiDAR 提供空间结构，IMU 提供短时姿态和运动变化，GNSS/RTK 提供室外全局坐标，相机提供图像和语义信息。融合的目标是让设备在复杂环境下定位更稳、建图更完整、数据结果更可靠。

## 7. 点云基础

### Q：点云是什么？

**回答：**

点云是由大量三维点组成的空间数据，每个点通常包含 X/Y/Z 坐标，有时还包含反射强度、颜色、时间戳等信息。手持 SLAM、三维扫描、机器人建图和空间测绘中，点云可以用于建模、测量、巡检、BIM 对比、地形分析等。

### Q：为什么会出现点云重影？

**回答：**

点云重影通常不是单一原因造成的，可能和轨迹估计误差、设备运动过快、环境特征不足、GNSS 状态变化、IMU 和 LiDAR 时间同步误差、传感器标定偏差、回环或重复路径有关。对客户不能简单说“算法会优化”，而是要结合具体场景、采集方式和测试数据判断，并通过采集 SOP、路线规划、速度控制和后处理流程来改善。

## 8. 时间同步为什么重要？

**回答：**

多传感器系统里，LiDAR、IMU、GNSS、摄像头采集数据的时间必须尽量对齐。如果时间不同步，设备在运动过程中同一时刻的姿态和空间点可能对应不上，最终表现为轨迹不稳、点云重影、边缘噪声、室内外切换偏移等问题。客户看到的是点云质量和轨迹稳定，研发关注的是时间戳、同步机制和数据链路。

## 9. 移动机器人常见传感器

|传感器|作用|优点|风险 / 限制|
|---|---|---|---|
|3D LiDAR|三维点云、建图、避障|不依赖光照，空间结构强|雨雾、玻璃、强反射可能影响|
|2D LiDAR|平面避障、定位|成本低、实时性好|只覆盖一个平面|
|RGB 相机|视频、图像识别、远程查看|信息丰富，客户直观|受光照、雾气、污渍影响|
|深度相机|近距离深度感知|适合避障、识别|室外强光下可能受影响|
|热成像|温度异常检测|电力、消防、巡检价值高|需要标定和阈值策略|
|IMU|姿态、角速度、加速度|短时响应快|长期漂移，需要融合|
|GNSS/RTK|全局定位|室外绝对坐标|室内、地下、林地、高楼遮挡弱|
|超声 / 毫米波|近距离障碍 / 特殊环境感知|可补充感知盲区|分辨率和可靠性受环境影响|
|气体传感器|有毒 / 可燃气体检测|应急、管廊、矿区有价值|需校准、寿命管理|
|麦克风 / 声学传感器|异响检测、救援搜索|可用于设备异常和人员搜救|受环境噪声影响|

# 七、特种行业业务场景知识库

[!important] 核心理解 特种行业客户买机器人不是为了新奇，而是为了解决危险环境替人、重复巡检提效、数据标准化留痕和复杂现场无人化作业的问题。所以方案不能只展示机器人能走，而要把任务闭环讲清楚：机器人怎么进去、怎么定位、怎么采集、怎么回传、怎么告警、怎么生成报告、怎么维护。

## 1. 特种行业客户的共同痛点

1. **环境危险**：高压电、坍塌风险、有毒气体、低温、高湿、粉尘、狭窄空间；
    
2. **人工成本高**：巡检、测绘、搜索、记录工作重复且耗时；
    
3. **人员风险高**：电力、隧道、矿区、灾害现场等不适合人员频繁进入；
    
4. **数据要求高**：需要视频、图像、热成像、点云、位置、告警记录；
    
5. **合规要求高**：安全作业、巡检记录、数据留痕、责任边界；
    
6. **部署环境复杂**：GNSS 弱、通信差、光照差、地形复杂、障碍多；
    
7. **客户决策保守**：需要 Demo、PoC、测试报告和可量化指标。
    

## 2. 测绘场景

### 客户痛点

- 人工测量效率低；
    
- 大范围或复杂空间采集成本高；
    
- 室内外切换、地下空间、树林遮挡导致 GNSS 不稳定；
    
- 需要点云、轨迹、坐标、三维模型等成果；
    
- 对精度、完整性和可重复性有要求。
    

### 机器人方案价值

- 搭载 LiDAR / 相机进行三维数据采集；
    
- 通过 SLAM 实现弱 GNSS 环境下建图；
    
- 通过 RTK/GNSS 或控制点进行全局坐标约束；
    
- 自动生成点云、轨迹、巡检影像；
    
- 减少人员进入危险区域。
    

### 面试可说

> 我之前做手持 SLAM 时，测绘客户最关注的是点云质量、轨迹稳定性、室内外切换和弱 GNSS 环境下的成果可用性。迁移到四足机器人上，核心逻辑类似，只是采集平台从人手持变成机器人自主或半自主移动。售前方案要明确机器人能输出什么数据、精度如何验证、哪些场景需要控制点或 RTK 约束，以及最终成果能否进入客户现有测绘和建模流程。

## 3. 建筑场景

### 客户痛点

- 工地环境复杂，障碍物多；
    
- 楼梯、坡道、门槛、临时通道多；
    
- 人员安全风险高；
    
- 需要施工进度记录、质量巡检、三维建模、沉降 / 变形辅助分析；
    
- 室内外切换容易影响定位和点云质量。
    

### 机器人方案价值

- 四足机器人具备楼梯、崎岖地面、狭窄空间通过能力；
    
- 搭载相机、LiDAR、热成像等载荷进行巡检和记录；
    
- 形成施工现场数字化留痕；
    
- 结合点云可辅助 BIM 比对、进度核查和安全巡检；
    
- 减少人员进入危险区域。
    

### 安全要求

- 作业区域隔离或提醒；
    
- 避免与施工机械、吊装区域交叉；
    
- 夜间作业需照明和警示；
    
- 机器人不得替代必要的人工安全判断；
    
- 高处、临边、坑洞等区域需路线规划和风险评估；
    
- 现场人员必须接受操作和急停培训。
    

### 日本建筑客户应答重点

> 对日本建筑客户，我不会一开始就强调机器人完全替代人工，而会强调它先从高频、重复、危险、需要留痕的任务切入，比如施工现场定期巡检、进度影像采集、三维数据采集、夜间安全巡查。先用 PoC 验证通过能力、数据质量和现场安全，再逐步扩大应用范围。

## 4. 巡检场景

### 典型行业

- 电力变电站；
    
- 电缆隧道；
    
- 地下管廊；
    
- 化工园区；
    
- 工厂厂区；
    
- 矿区；
    
- 水利设施；
    
- 公共安全巡逻。
    

### 巡检任务类型

|任务|机器人载荷|
|---|---|
|仪表读数|RGB 相机、OCR 算法|
|温度异常|红外热成像|
|声音异常|麦克风 / 声学传感器|
|气体泄漏|气体传感器|
|设备状态|可见光视频、图像识别|
|环境建图|LiDAR、SLAM|
|异常告警|后台平台、规则引擎|

### 面试可说

> 巡检场景不是机器人走一圈就完成了，真正价值在于从任务规划、路径执行、数据采集、异常识别、告警推送、报告生成到问题闭环的全流程。售前方案中要先确认客户巡检对象、巡检频率、识别项、告警规则和验收标准，再选择机器人本体、传感器载荷和平台接口。

## 5. 林地测量与林业巡检场景

### 客户痛点

- 林地 GNSS 弱，遮挡严重；
    
- 地形起伏大，坡度、泥泞、树根、落叶影响移动；
    
- 人工作业效率低且安全风险高；
    
- 需要树木、地形、道路、灾害隐患等数据；
    
- 通信覆盖差，数据回传困难。
    

### 机器人方案价值

- 四足 / 轮足机器人适合复杂地形；
    
- LiDAR 可采集林下空间结构；
    
- 可搭载相机、热成像、气体 / 环境传感器；
    
- 可用于林地测绘、巡检、灾害排查、道路勘察；
    
- 可减少人员进入危险区域。
    

### 风险边界

- 茂密植被可能影响 LiDAR 视野；
    
- 雨雪泥泞会影响足端摩擦；
    
- 坡度过大存在跌倒风险；
    
- GNSS 不可用时需要依赖 SLAM 和局部地图；
    
- 无网络区域需支持离线记录和任务后导出。
    

### 面试可说

> 我之前做林地测量方案时，客户非常关注树林遮挡、弱 GNSS、轨迹漂移和点云质量。对四足机器人来说，林地场景要重点评估地形通过能力、SLAM 稳定性、通信覆盖和任务边界。我的思路是先做小范围 PoC，验证机器人在典型林地道路、坡道、泥泞地面和树木遮挡下的通过能力与数据质量，再评估是否扩大部署。

## 6. 应急救援与危险环境

### 典型场景

- 地震、坍塌后搜索；
    
- 火灾后建筑内部探查；
    
- 化工泄漏区域侦察；
    
- 隧道事故；
    
- 矿区事故；
    
- 辐射或有毒环境探测。
    

### 机器人价值

- 替代人员进入危险区域；
    
- 提供实时视频、热成像、声音、气体数据；
    
- 建立现场态势感知；
    
- 发现人员、火源、泄漏点、障碍物；
    
- 为救援指挥提供数据支撑。
    

### 售前表达

> 应急救援场景不能承诺机器人解决所有问题，因为现场具有极强不确定性。更稳妥的表达是：机器人可以作为前出侦察和态势感知工具，帮助人员在进入危险区域前获得视频、热成像、气体、声音和空间结构信息，从而降低人员风险，提高决策效率。

# 八、日本 / 海外客户应答材料

## 1. 日本市场为什么适合特种机器人

日本对特种机器人有较强需求，主要来自：

1. **少子老龄化和劳动力不足**：建筑、基础设施、林业、巡检等行业用人压力大；
    
2. **基础设施老化**：桥梁、隧道、道路、港口等设施需要周期性检查；
    
3. **自然灾害频繁**：地震、台风、暴雨、山体滑坡等灾害场景需要机器人辅助侦察；
    
4. **工业安全要求高**：企业愿意用机器人降低人员进入危险区域的频次；
    
5. **客户对流程和文档要求高**：重视测试报告、SOP、培训、维护和责任边界。
    

面试表达：

> 我理解日本市场对机器人并不是只看技术先进性，而是非常关注安全、可靠、文档、现场验证和长期维护。比如建筑、基础设施巡检、林业、灾害救援等场景，日本都存在劳动力不足、人员安全和高频巡检的需求。机器人出海日本市场，适合从巡检、建筑工地、隧道管廊、林地测量和应急侦察这些特种场景切入。

## 2. 日本客户沟通特点

日本客户常见关注点：

- 是否有详细技术资料；
    
- 是否有英文 / 日文 PPT、手册、SOP；
    
- 是否有测试报告和实测数据；
    
- 是否明确产品边界；
    
- 是否符合当地安全和认证要求；
    
- 是否能提供培训和售后；
    
- 是否能稳定供货和备件支持；
    
- 是否能和现有业务流程结合；
    
- 出现问题后如何升级、响应和复盘。
    

面对日本客户，要避免：

- 过度承诺；
    
- 只讲参数；
    
- 只说“没问题”；
    
- 不讲限制条件；
    
- 不提供文档和测试计划。
    

更好的方式：

> 先确认场景 → 再确认风险 → 再设计 PoC → 用数据验证 → 输出报告 → 明确下一步。

## 3. 日本市场合规要点｜面试层面

[!warning] 注意 以下内容用于面试表达，不作为法律意见。正式项目应由公司合规、认证机构和当地合作伙伴共同确认。

### 无线通信认证

机器人如果使用 WiFi、蓝牙、4G/5G、遥控链路等无线模块，进入日本市场需要关注当地无线电相关认证和技术适合性要求。

面试表达：

> 如果机器人进入日本市场，我会提前确认通信模块是否已有日本当地认证，特别是 WiFi、蓝牙、4G/5G、遥控链路等。售前阶段不应只看机器人功能，还要把无线合规和频段适配作为进入日本市场的前置检查项。

### 电气安全和 PSE

如果涉及充电器、电源适配器、部分电池或电气产品，需要关注日本 PSE 等电气安全要求。

面试表达：

> 对日本项目，我会把机器人本体、充电器、电池、无线通信模块和任务载荷分开确认合规边界。售前阶段不一定由我完成认证，但我会提醒团队和客户提前确认认证状态、适用范围和交付责任。

### 工业现场安全

机器人进入建筑、工厂、电力、管廊等现场，要关注急停、限速、人员安全距离、警示、操作培训、现场风险评估和应急处置流程。

面试表达：

> 日本客户通常比较重视现场安全和责任边界。我会在方案中明确机器人适用区域、操作人员要求、急停方式、通信失联策略、限制条件和现场测试计划，避免客户以为机器人可以无条件自主运行。

## 4. 日本客户可能问答

### Q1：你们的机器人在日本建筑工地安全吗？

**回答：**

我不会简单回答“绝对安全”。我会先说明机器人安全需要结合具体工地环境来评估，包括楼梯、坡道、临边、坑洞、施工机械、人员密度、通信覆盖和作业时间。方案上会通过限速、急停、安全距离、路线规划、风险区域避让、操作培训和现场 SOP 来降低风险。正式部署前建议先进行小范围 PoC，验证通过能力、避障能力、通信稳定性和人员协同流程。

### Q2：日本现场很多楼梯、狭窄通道和临时障碍，机器人能稳定工作吗？

**回答：**

机器人具备一定复杂地形通过能力，但是否稳定工作要看现场楼梯高度、通道宽度、地面材质、障碍物类型和任务路线。我的建议是先选择典型路线做 PoC，把楼梯、坡道、狭窄通道、临时障碍和通信盲区纳入测试项，用通过率、任务完成率、人工接管次数和异常记录来判断是否适合扩大部署。

### Q3：你们能不能保证点云精度？

**回答：**

点云精度需要结合测试条件和验收指标来确认。不同场景下，相对精度、绝对精度、建模可用性和巡检可用性要求不一样。我们可以根据客户典型场景设计测试路线，用控制点、对比测量或标准物体进行验证，输出测试报告。这样比口头承诺更可靠。

### Q4：日本客户比较保守，为什么要用中国机器人？

**回答：**

我会从应用价值而不是“国家标签”去回答。客户最终关注的是机器人能不能降低人员风险、提高巡检效率、输出稳定数据、降低长期维护成本。如果产品能通过 PoC 证明稳定性、通过文档说明安全边界、通过售后体系保证维护响应，就有机会建立信任。对日本客户，技术先进只是基础，真正打动客户的是可靠性、流程、数据和长期支持。

### Q5：机器人在日本需要哪些认证？

**回答：**

这个问题需要结合具体产品配置确认。一般要关注无线通信模块、电气安全、电池和充电器、工业现场安全、数据合规等方向。售前阶段我不会直接给客户不确定的认证结论，而是会确认产品已有认证清单、适用国家和适用型号，再和公司合规、认证机构以及当地合作伙伴一起判断。

### Q6：如果现场通信不好怎么办？

**回答：**

我会先区分是遥控链路、视频回传、任务数据上传，还是后台平台通信受影响。方案上可以考虑本地遥控、专网 / 5G / WiFi 覆盖优化、离线任务缓存、断点续传、低码率视频策略、任务完成后批量上传等方式。对客户要说明：通信不好不一定意味着机器人完全不能工作，但会影响实时视频、远程控制、数据回传和安全接管能力，所以必须在 PoC 中验证。

### Q7：机器人坏了怎么办？维护谁负责？

**回答：**

海外项目需要提前定义售后和维护机制，包括远程诊断、日志上传、备件支持、代理商一线处理、总部二线支持、软件升级和硬件返修流程。售前阶段我会把维护周期、易损件、培训内容、响应机制和责任边界写清楚，避免交付后客户不知道找谁、怎么处理。

我是电子信息硕士，具备机器人、SLAM、RTK、多传感器融合和嵌入式系统背景。我的优势不是单纯研发或传统销售，而是技术型解决方案能力。

在司南导航，我参与手持 SLAM 扫描设备的产品验证、行业方案输出、海外客户技术支持和售前材料沉淀，涉及激光雷达、IMU、GNSS、摄像头、点云采集和三维重建。我做过测绘、建筑、巡检、林地测量等场景的需求拆解和技术方案，也参与日本、北欧客户的技术答疑、英文材料和 Issue 闭环。

在研究院，我参与集群机器人科研成果向教育场景转化，做过机器人 Demo、人工智能实训室方案、院校客户演示、招投标材料和交付反馈。

我适合解决方案岗位，是因为我能理解技术，也能把技术转化成客户价值；能写方案、做演示、答疑，也能把客户问题反馈给研发推动闭环。

最终人设记住一句话：

> 我不是纯算法研发，也不是传统销售，而是懂技术、会方案、能沟通、能验证、能闭环的技术型解决方案工程师。

## 2. 必背短句

- 方案不是产品介绍，而是客户问题的解决路径。
    
- 售前不能只说产品很好，而要让客户知道为什么能用、怎么验证、哪些场景需要注意。
    
- 客户说的是“能不能用”，研发看的是“问题在哪个链路”。我的价值是把两种语言翻译清楚。
    
- PoC 不是简单试用，而是带目标、带指标、带报告的验证过程。
    
- Issue 不是转发客户抱怨，而是把模糊反馈变成研发可复现、可判断、可处理的问题单。
    
- 海外客户尤其重视文档、数据证据、风险边界、责任划分和长期维护。
    
- 我不会过度承诺所有场景都稳定，而是建议用客户典型工况做验证。
    
- 我不是 SLAM 核心算法负责人，但我理解 SLAM 在产品中的作用，能把轨迹、点云、重影、弱 GNSS 等问题和客户体验对应起来。
    

## 3. 面试收尾表达

如果有机会加入，我希望能够先从产品体系、典型行业方案、海外客户材料和标准化 PoC 流程熟悉起，尽快参与客户技术交流、Demo 支持、Issue 闭环和行业方案沉淀。我比较适合做技术和客户之间的连接型角色，也愿意在机器人出海和特种行业落地场景中继续深入。
